## 已确认的原因

- 六项单位冲突全部是同一物料编码，在六个销售合同下分别出现两张相同的采购单来源。每组两个原始 id 不同；需求身份字段相同（编码/名称/颜色/规格/需求数量等），单位分别为两个不同的计数用语。两张采购单分别带有不同的入库、出运、出库单号，各组数量相等。没有证据显示是不同编码错误归并或哈希碰撞；但来源没有独立需求行主键证明它们是一个需求。需核实重开/替代/补单还是两批真实业务，不能按等量删除事件，也不能擅自建立单位别名。
- 六个颜色异常均有数量及所有尺码字段全空的行；其中三个合同只有具名空颜色，另三个还各有两个颜色名也空的行。已有非空颜色尺码数量可核对。当前 Adapter 将任一 INVALID_SIZE_NUM/空身份视为合同颜色不完整，故全量首绑被阻止。空行看起来像模板占位是推断，不是允许丢弃的规则。
- 一合同采购单存在两行负采购量，一张入库单有负入库量。来源字段本身为负，不是织序减法或浮点产生。退料/冲销/录入错误未确认；保留 signed 原始事实，齐套保持 unknown，不能按绝对值或零计算。
- 四个空物料合同在完整分页及再次指定查询仍返回零行。两个来源状态草拟、两个生效；一个生效合同的 InsideOrderNo 包含取消文字，但 Num 仍正值。说明仅按状态或文字推断已取消不可靠。其余可能是未申购或报表关联缺漏，需查看申购明细及内部订单号。
- 理论用量与实际采购不同是两个合法事实，不归类为上述异常。原有需求 TotalNum、采购 cgnum 和正式齐套规则不修改；已验证的两来源行同一采购事件仍保持去重。

## Server 报价转订单的实际缺口及实施约束

Browser 已有版本选择和本地 `createOrderFromQuote`；Server 编辑器明确禁用生成订单。Server `createSalesOrder` 已支持 quote provenance，但没有受控创建路由、幂等收据及报价订单业务快照；列表/detail 查询只连接艾诺科镜像，因此只插 sales_orders 会得到空款号/空数量。

独立 PR 需增加 forward-only quote-order snapshot/receipt，事务内重新核对权限、锁定 exact Quote+Revision+PriceVersion、Quote CAS、服务端订单号与审计，复用 CCT exact provenance。仅建立关联，不把报价测算售价或工价直接当成当前确认值；多个订单允许关联同一 CCT。不读 Browser storage，不制作伪造 Ainuoke source link。沿用已批准 Modal；正式新建量与日期等非来源字段显式输入，响应不泄露成本。测试涵盖版本不存在/过期、伪造actor或订单号、幂等重试与并发、审计失败回滚、CCT权限及关联不漂移、所有读取表面。
