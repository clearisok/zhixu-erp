# Issue #174：织序同步存储架构整改与数据库容量治理

## 一、任务背景

基于 Issue #174 已完成的数据库体积调查，现决定对织序自动同步的数据存储架构进行专项整改。

调查已经确认：

- Staging PostgreSQL 数据库容量为 12.336 GB。
- 当前订单仅636张。
- 艾诺科原始响应占8.318 GB。
- 历史快照与版本占2.893 GB。
- 最大三张表合计占数据库容量的92.11%。
- `ainuoke_source_runs` 每次成功同步单个合同时，重复保存完整合同目录。
- `discovery` 字段累计占用7.964 GB。
- `ainuoke_contract_observations` 与 `ainuoke_material_source_snapshots` 存在物料正文重复存储。
- 最近7天42,398次物料发布中，99.38%被现有审计标记为无新增、无更新，但仍产生物理发布记录。
- 当前内容哈希包含采集时间，导致相同业务正文无法有效去重。
- 同步日志、历史快照、采集证据目前缺乏合理的生命周期管理。
- `ainuoke_sync_audit_record_state` 已产生约1,010万次UPDATE。
- 当前颜色镜像存在大量无变化情况下的删除重插。
- 按现有模式持续运行，未来数据库可能增长至数百GB。

上述问题属于存储架构设计问题，不应继续通过增加硬盘容量、延长备份超时时间或降低同步频率来解决。

将 Issue #174 定义为 P0 优先级整改任务。

## 三、正式批准的数据保留规则

以下规则作为本次技术设计的业务输入，不再反复向我确认。

| 数据类型 | 保留期限 |
|---|---|
| 正式订单及业务数据 | 长期保留 |
| 报价、商业版本、财务、生产、关账历史 | 长期保留 |
| 人工业务操作及权限审计 | 长期保留 |
| 真实来源变化历史 | 长期保留 |
| 当前有效来源数据及必要证据 | 持续保留 |
| 普通同步成功日志 | 7天 |
| 无变化的采集详细证据 | 7天 |
| 已解决的失败日志 | 30天 |
| 临时诊断与分页检查点 | 7天 |
| 每日同步汇总统计 | 90天 |
| 旧重复历史迁移后的原始备份 | 90天 |
| 未解决异常及未知结果 | 保留至解决，并按后续适用期限处理 |
| 被正式业务引用的历史及证据 | 按业务引用及适用保留要求持续保护 |

### 保留规则的例外

任何自动到期规则不得删除：

- 当前订单正在使用的数据。
- 当前有效的物料、合同、颜色及其他来源版本。
- 被报价、生产、关账、财务或正式业务版本引用的证据。
- 尚未解决的同步异常。
- 尚未确定最终提交结果的任务及回执。
- 正在执行或等待恢复的任务所依赖的记录。
- 必要的幂等身份和防重复提交记录。
- 仍被其他有效记录引用的共享正文。
- 依法或按业务审计要求必须继续保留的记录。

失败日志30天的期限从故障解决时间开始计算，而不是从故障首次发生时间计算。

旧历史原始备份的90天保留期限，从正式迁移验收成功后开始计算；到期前必须确认恢复能力及迁移验收结果。

该90天规则仅针对本次历史迁移形成的专项原始备份，不代表修改现有日常备份保留策略。

## 四、不可改变的业务原则

1. 艾诺科是外部来源数据系统，织序是业务管理系统。
2. 保证当前业务数据真实、完整、准确。
3. 相同来源正文原则上只保存一份。
4. 真实来源内容发生变化时，才生成新的业务历史版本。
5. 采集时间变化不代表业务内容变化。
6. 同步成功不代表必须产生新的业务历史版本。
7. 必须保留必要的同步新鲜度、成功失败状态及来源追溯能力。
8. 不需要永久保存每次无变化同步的全部过程数据。
9. 临时运行日志和诊断数据必须具备明确生命周期。
10. 数据库长期增长应主要来自实际业务增长及真实数据变化，而不是同步次数。
11. 不得为减少数据库体积而降低来源校验标准。
12. 不得改变现有订单、物料、报价、财务、生产及关账业务规则。

## 五、技术整改设计要求

### 5.1 完整合同目录共享存储

最高优先级。

重点检查：

- `ainuoke_source_runs`
- `ainuoke_catalog_runs`
- `ainuoke_catalog_capture_evidence`
- `ainuoke_catalog_evidence_chunks`

现有问题：

每次成功同步一个合同，`ainuoke_source_runs.discovery` 都会保存完整合同目录，而系统已经存在共享目录及目录内容块去重机制。

整改要求：

- 优先复用现有共享目录机制，不另建功能重复的系统。
- 相同目录正文只保存一份。
- 多个合同同步记录引用对应的共享目录证据。
- 每次实际采集的时间、来源、完整性结果与正文内容分开保存。
- 保留目录双遍校验、完整性检查、账号及来源身份保护。
- 保留订单新增、删除、恢复以及目录范围变化识别能力。
- 不得因为目录正文复用而跳过现有必须执行的来源校验。
- 不得错误地让历史记录引用不断变化的当前目录。
- 保证历史目录引用可准确重建当时对应的来源内容。

目标：

彻底消除每次单合同同步重复保存整份合同目录的问题。

### 5.2 物料正文跨表共享

重点检查：

- `ainuoke_contract_observations`
- `ainuoke_material_source_snapshots`
- `ainuoke_material_order_heads`

现有问题：

合同观察记录与正式物料快照重复保存相同物料数组。

整改要求：

- 将相同物料正文改为共享存储。
- 合同观察与物料快照继续保留各自必要的业务职责、身份和引用关系。
- 不重复保存相同的完整物料正文。
- 保留采购、入库、出运、需求及单位核对所依赖的全部必要来源事实。
- 保留当前版本指针与历史版本的正确关联。
- 共享正文必须不可变，不允许某一引用方修改正文后影响其他历史记录。
- 不得根据款号、数量相同等不充分条件判断两份数据相同。
- 必须考虑来源身份、合同身份、报表类型、字段语义及数据结构版本。
- 保证共享正文的读取、恢复与历史追溯能力。

优先选择简单、可靠、可复用的数据结构，避免为去重引入不必要的新服务。

### 5.3 无变化时不新增业务历史版本

将现有哈希机制明确区分为：

**业务内容哈希（Business Content Hash）**

用于判断来源业务内容是否发生真实变化。

**采集证据哈希（Capture Evidence Hash）**

用于验证一次实际采集的完整性及来源证据。

要求：

- `fetchedAt` 等纯采集时间字段不参与业务内容变化判断。
- 保留原始采集时间，不得因此丢失数据新鲜度信息。
- 逐项明确哪些字段属于业务事实，哪些属于采集元数据。
- 不得简单删除所有时间字段；业务日期、交期、出运日期、入库日期等必须保留。
- 不得通过忽略金额、数量、单位、来源身份等重要字段获得虚假的去重效果。
- 正确处理空值、空字符串、重复行、行顺序、数值精度和来源记录删除。
- 对哈希规范进行版本管理，并明确兼容策略。
- 内容相同后应具备必要的等价性验证，不得仅凭不可靠的弱哈希合并历史。

预期行为：

| 场景 | 正确行为 |
|---|---|
| 首次同步 | 创建初始业务版本 |
| 再次同步且内容相同 | 不新增业务版本 |
| 数量发生变化 | 新增真实业务版本 |
| 供应商、规格或单位变化 | 按真实变化规则新增版本 |
| 仅采集时间变化 | 更新同步确认信息 |
| 来源订单删除 | 保留删除生命周期证据 |
| 来源订单恢复 | 保留恢复生命周期证据 |
| 来源数据由A变为B再变回A | 保留三次业务状态事件，但A正文可以共享 |
| 同步失败 | 保留上一有效版本，不错误标记成功 |
| 来源结果不完整或未知 | 保留现有安全保护机制 |

无变化同步仍必须正确更新：

- 最近成功同步时间。
- 最近尝试时间。
- 当前同步状态。
- 下次计划同步时间。
- 必要的来源校验结果。
- 必要的任务回执与幂等状态。

不得因为复用业务历史版本而让页面误认为数据长期未刷新。

### 5.4 日志分类及生命周期管理

重点检查：

- `operation_logs`
- `ainuoke_sync_audit_tables`
- `ainuoke_sync_audit_batches`
- `ainuoke_sync_jobs`
- `ainuoke_sync_capture_attempts`
- `ainuoke_catalog_runs`
- `ainuoke_catalog_capture_evidence`
- `ainuoke_catalog_scan_pages`
- `ainuoke_catalog_diagnostics`

设计时必须区分：

1. 正式业务操作审计。
2. 普通同步成功日志。
3. 无变化采集证据。
4. 已解决失败日志。
5. 未解决故障及未知结果。
6. 临时诊断和分页检查点。
7. 被业务引用的必要来源证据。
8. 每日同步汇总统计。

不得将整张混合用途的表简单判定为可删除日志表。

例如，`operation_logs` 中的人工操作审计应长期保留，而普通自动同步过程日志按照7天规则管理。

要求：

- 按实际数据性质、引用关系及任务状态确定清理资格。
- 设计统一、简单、可审计的TTL保留机制。
- 不引入不必要的独立微服务。
- 支持清理前预览（Dry Run）。
- 支持小批量清理、执行限速及锁等待保护。
- 清理任务可重复执行且不会误删数据。
- 不允许因定期清理产生新的无限增长日志。
- 清理结果应记录处理范围、数量、失败原因及必要审计信息。
- 未完成任务、在途任务、未知结果及未解决异常不得进入普通清理流程。
- 对共享正文进行清理时，必须证明不存在有效引用。
- 如现有不可变触发器与新保留规则冲突，应设计明确受控的生命周期管理机制，不得简单取消全部不可变保护。

每日汇总至少包含：

- 同步日期。
- 计划任务数。
- 实际同步合同数。
- 成功次数。
- 失败次数。
- 无变化次数。
- 真实变化次数。
- 重试次数。
- 平均及必要的高分位耗时。
- 新增正文数量。
- 新增数据量统计。

每日汇总保留90天。

设计应考虑重复执行、跨日任务、失败重试和汇总数据重复计算问题。

### 5.5 减少数据库写放大

重点检查：

- `ainuoke_sync_audit_record_state`
- `ainuoke_sales_order_color_mirrors`
- `ainuoke_sales_order_contract_mirrors`
- `ainuoke_material_order_heads`
- 其他无变化情况下频繁UPDATE或DELETE/INSERT的路径。

要求：

- 内容未发生变化时，不重复更新相同业务字段。
- 避免无变化情况下先删除颜色记录再重新插入。
- 保留稳定的订单和颜色业务身份。
- 对当前镜像实施必要的差异化更新。
- 将同步新鲜度状态与业务内容更新分开处理。
- 不破坏逻辑变更统计所需的状态和批次关联。
- 不降低任务幂等性、事务原子性及错误恢复能力。
- 不因减少写入而丢失必要的成功回执。
- 不得引入更复杂且难以验证的缓存一致性机制。

需要量化整改前后的：

- INSERT数量。
- UPDATE数量。
- DELETE数量。
- WAL写入量。
- 数据库新增字节量。
- 同步耗时。

## 六、现有同步策略保持不变

本次不通过降低同步频率解决存储问题。

保留现有：

- 高频同步策略。
- 每日同步策略。
- 每周同步策略。
- 每月同步策略。
- 手动刷新功能。
- 当前合同分档规则。
- 既有来源身份、完整性与一致性保护。

自动同步、手动同步、重试及恢复路径均应遵守新的存储规则。

不得只修复其中一个入口，导致其他入口仍然重复保存完整正文。

## 七、同步与维护任务的故障隔离

本次调查发现Worker已处于 `catalog_diagnostic_write_failed` 暂停状态。

请单独核对该异常与来源诊断存储、数据库写入及同步正确性的关系。

在设计中明确故障分级：

### 必须保留安全阻断的情况

- 来源身份不可信。
- 来源数据不完整。
- 提交结果未知。
- 必要业务数据写入失败。
- 无法确认事务提交状态。
- 来源证据损坏或无法验证。
- 可能造成业务数据错误的异常。

### 应评估局部隔离的情况

- 非关键成功日志写入失败。
- 普通历史日志清理失败。
- 每日统计生成失败。
- 非关键临时诊断资料写入失败。
- 不影响当前业务正确性的维护任务失败。

设计原则：

普通辅助维护任务的失败，不应无条件导致全部订单自动同步停止。

但如果该任务涉及必要的来源证明或数据完整性，则必须保留相应安全保护。

必须根据实际依赖关系设计，不得统一取消所有暂停机制。

本轮不得擅自恢复当前暂停的Worker，也不得绕过现有恢复门禁。

如果发现新的故障修复需求，单独记录原因、风险与建议实施范围。

## 八、历史数据迁移方案

不仅要解决未来重复写入，还要制定现有12.336 GB数据库的安全缩减方案。

优先考虑无损去重，而不是直接删除历史记录。

### 8.1 历史引用调查

明确：

- 三张主要大表的完整读写路径。
- 外键、逻辑引用及JSON内嵌引用。
- 当前订单与最新快照的关系。
- 业务历史版本与来源证据的关系。
- 历史回放及恢复流程。
- 不可变触发器的保护对象。
- 现有API、页面、测试及运维脚本的依赖关系。

不能只检查数据库外键而忽略代码中的逻辑引用。

### 8.2 迁移前保护

设计：

- 完整数据库及对象存储配对备份。
- 原始备份的完整性验证。
- 实际隔离恢复演练。
- 数据库容量及磁盘空间预算。
- 迁移期间WAL、临时文件、归档文件和新旧数据共存的峰值预算。
- 明确的回滚策略。

当前调查显示主机磁盘已使用约83%，可用空间约39.7 GB。

不得假设现有磁盘一定能够承受新旧数据库、备份及迁移临时文件同时存在。

如空间不足，应优先考虑独立磁盘或隔离主机进行迁移演练。

### 8.3 历史正文去重

设计可重复执行、支持中断恢复的迁移流程：

1. 识别历史目录正文。
2. 识别相同目录版本。
3. 建立或复用共享目录引用。
4. 识别历史物料正文。
5. 建立跨表共享引用。
6. 分离业务版本与采集时间。
7. 保留真实变化历史。
8. 根据已批准的期限识别符合到期条件的过程记录。
9. 验证所有现存业务引用。
10. 验证历史重建与查询结果。

必须明确哪些优化属于无损去重，哪些属于按保留策略主动放弃的历史过程数据。

不能将二者混为一谈。

### 8.4 历史数据验收

迁移前后需要核对：

- 636张订单及实际现场最新订单集合。
- 所有稳定订单身份。
- 所有合同来源绑定。
- 当前物料版本。
- 需求、采购、入库、出运数量与单位。
- 成衣颜色、尺码与数量。
- 报价及价格版本。
- 人工业务数据。
- 生产、财务及关账数据。
- 订单删除和恢复历史。
- 用户、角色及权限。
- 附件及对象存储引用。
- 真实来源变化历史。
- 仍受保护的异常和诊断证据。

验收原则是业务数据与业务行为等价，而不是要求优化后所有技术表的物理行数保持不变。

### 8.5 物理空间回收

必须区分：

- 删除逻辑数据。
- PostgreSQL内部空间复用。
- 实际返还操作系统磁盘空间。

评估表重建、受控数据库迁移、VACUUM FULL或其他适用方式的优缺点。

不得默认选择会造成大量锁定、磁盘临时占用或长时间停机的操作。

要求说明：

- 所需维护窗口。
- 是否影响应用访问。
- 是否需要短暂停止Worker。
- 预计磁盘峰值。
- 预计空间释放量。
- 失败恢复方式。

历史迁移后的原始备份保留90天，并与正式日常备份策略分开管理。

## 九、数据库容量监控

设计轻量化容量监控，不需要为此新增复杂的监控平台或独立业务模块。

建议每日采集：

- 数据库总容量。
- 主要表容量。
- TOAST容量。
- 索引容量。
- 每日新增空间。
- 共享正文新增数量。
- 同步成功次数。
- 真实业务变化次数。
- 无变化同步次数。
- 最新成功同步时间。
- 备份耗时。
- 归档体积。
- 主机磁盘剩余空间。
- WAL及临时文件占用的必要指标。

容量监控记录的保留期限建议90天，作为设计方案的一部分提交确认。

建议预警：

- 主机磁盘使用率达到70%：普通预警。
- 主机磁盘使用率达到85%：严重预警。
- 数据库增长速率明显超过已验证的正常范围：异常预警。
- 预计剩余磁盘不足以支持安全备份或迁移：专项预警。

预警不应直接等同于暂停全部业务服务；应结合真实安全风险决定处理方式。

## 十、工程验收目标

| 指标 | 目标 |
|---|---|
| 完整合同目录重复正文 | 消除 |
| 相同物料正文跨表重复存储 | 消除 |
| 无变化时新增业务历史版本 | 0 |
| 来源真实变化识别 | 正确且完整 |
| 正式业务数据丢失 | 0 |
| 当前有效版本丢失 | 0 |
| 历史有效引用断裂 | 0 |
| 业务金额、数量、单位错误 | 0 |
| 自动同步频率 | 保持现有策略 |
| 同步状态及新鲜度 | 正确 |

| 同步性能 | 不低于现有可比基线 |

不得为了满足容量数字而删除必要业务记录、降低来源校验要求或绕过安全保护。

## 十一、建议实施批次

请在设计方案中明确每批实际改动范围、依赖关系、数据库迁移方式、测试要求和验收标准。

原则上按照以下顺序设计：

### 批次A：阻止完整目录重复保存

解决最大的存储增长来源，复用已有共享目录机制。

### 批次B：共享物料正文及内容哈希分离

### 批次D：日志保留及生命周期管理

建立TTL、每日汇总、清理资格判断、引用保护与维护故障隔离。

在隔离环境演练全部现有历史数据的迁移、验证、恢复及空间缩减。

### 批次F：容量监控及组合验收

验证整个整改方案在持续同步、正常备份和异常恢复情况下的实际效果。

## 十二、测试与验收要求

方案必须包含以下测试场景：

- 连续多次采集完全相同的合同目录。
- 多个合同共享相同目录正文。
- 同一合同连续多次采集完全相同的物料内容。
- 仅采集时间发生变化。
- 需求、采购、入库、出运数量分别发生变化。
- 规格、供应商、单位、价格等业务字段变化。
- 数据由A变为B再变回A。
- 来源记录新增、删除与恢复。
- 空结果与不完整结果。
- 重复记录及行顺序变化。
- 手动同步与自动同步并发。
- 任务失败重试。
- 事务中断及提交结果未知。
- 旧格式与新格式混合读取。
- 历史引用重建。
- 日志达到保留期限。
- 被业务引用的过期日志不得删除。
- 未解决异常不得清理。
- 清理任务重复执行及异常中断。
- 共享正文并发写入。
- 共享正文仍存在有效引用。
- 数据库备份与恢复。
- 应用版本回滚。
- 数据迁移中断后恢复。
- 现有订单、报价、物料、生产、财务及关账页面回归。

性能验收应采用相同合同范围、相同来源内容、相近运行环境及一致统计口径进行整改前后对照。

不得将不同同步次数或不同业务负载的数据直接比较。

最终实施阶段应至少完成两轮真实自然调度周期的正确性验证，并取得不少于24小时的实际容量增长观察数据。

如果24小时观察尚未完成，应明确区分功能验收与长期容量验收，不得提前宣称全部目标实现。

## 十五、总体设计原则

本次整改的目标是让织序更加简单、稳定、易于维护，而不是建立一套更加复杂的数据治理平台。

优先复用现有数据库、共享目录机制、任务调度及备份能力。

不要为了完成本次整改，额外引入Redis、Kafka、Elasticsearch、独立数据仓库、新微服务或其他非必要基础设施。

可以接受必要的数据库结构调整，但每一项新增结构都必须有明确用途。

如果一个问题可以通过简单的正文共享、内容比较、状态更新及定期清理解决，就不要引入复杂架构。

最终目标：

**数据有变化才产生新的业务历史，相同正文只保存一份，过程日志按期限保留，正式业务永久受到保护，订单同步持续稳定运行。**
