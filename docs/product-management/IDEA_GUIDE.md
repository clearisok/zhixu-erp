# 想法记录与调研

直接用自然语言告诉 Codex，或使用仓库的“产品想法”表单。除标题外均可留空，不要求用户先写技术方案。给 Issue 加 `product` 和 `idea`；已有同一需求时先展示对应链接，避免重复创建。Issue Forms 合并到默认分支后才作为正式入口验证。

## 记录原则

正文保留“我的想法、希望解决的问题、当前处理方式、期望效果、截图及附件、其他补充”。未知内容留空或标待确认，不代替用户编造。只把原始想法记入 Idea，不启动开发或部署。附件先脱敏，不能提交账号密码、Cookie、Token、原始私有业务导出或备份。

`product` 是纳入 Project 的统一标签；`idea / feature / improvement / bug / research / audit / refactor / tech-debt` 描述工作性质，不表示授权或生命周期。分类可并存，生命周期只使用 Project Status。现有标签复用，不覆盖其颜色/说明。没有用户批准时，不擅自迁移、重分类或关闭旧登记事项。

## Research 的最小交付

1. 用户原始目标、成功标准草案、不做什么及环境边界。
2. 现有实现：文件与行号、接口、数据库结构、已有文档/测试；事实、推断和无法验证项分开。
3. 与既有 Issue、PR、交付能力的重叠，依赖及兼容性。
4. 业务与数据风险、权限、数据保留/恢复要求，以及需要用户回答的不可替代业务事实。
5. 可选方案及收益/代价，不把推荐当决定；建议下一步。

Research 默认只读。读取真实业务数据、外部来源、登录或权限不足时，先核对既有授权和最小必要范围，不因进入 Research 自动扩大权限。缺事实只影响相关部分，继续可独立推进的只读核查。

## Design 的版本化方案

在 Issue 中发布 `方案 v1`，以后用 v2、v3 并列保留差异。包括业务规则、页面/交互设计（无 UI 时说明）、技术与数据流、影响文件/模块、权限及人工数据保护、依赖、实施步骤、必要测试、实际验收步骤、发布范围、兼容性与回滚方式、风险/未决项。将验收标准写成可观察结果，不只列开发动作。

请用户批准具体版本。用户决定需按 [生命周期规范](WORKFLOW.md#授权记录)记录；未批准前不进入 Ready 或修改业务实现。若当前请求本身已经明确授权完整的具体实施范围，应记录对应原始请求，不额外制造一轮内部技术选择审批，也不能借此覆盖未授权部分。
