# Issue174 精简整改决策方案 v2

2026-11-24；**Design / 待评审，仅方案评估**。Refs [Issue174](https://github.com/clearisok/zhixu-erp/issues/174)。本方案窄替代[v1.1](Issue174-同步存储架构整改与数据库容量治理实施方案.md)的全量历史转换、长期混读和迁移组件路线；双hash、全部入口、业务保护及验收标准继续适用。未执行数据库调查、删除、迁移、配置、部署或Worker恢复。

## 1. 建议决定：选择性迁移，建立新的来源历史起点

**推荐采用。** 以正式业务、当前有效来源和受保护历史为迁移根，只迁入其完整依赖闭包，在独立目标库建立统一的新存储格式。允许不迁入已证明无业务引用、无其他保留义务的旧来源变化、重复正文及无价值过程详情；不再为它们开发无损转换或历史重建。

Codex转录本次聊天用户决定：“允许将本次整改作为新的来源历史记录起点，整改后的真实来源变化按照新结构长期保留。”“本轮仍为方案评估，不授权实际删除、迁移、部署或恢复暂停的Worker。”这改变了整改前旧来源历史的保留目标，**不是实际删除或切换授权**。切换点T以未来验收记录固定；业务源时间保持原值，不能把T伪造成刚完成源站同步。

## 2. 与v1.1对比：放弃什么，取消什么

| 项目 | v1.1 | 精简v2 |
| --- | --- | --- |
| 旧来源变化与重复采集正文 | 全量E1无损转换，另做E2到期 | 无引用、无保留义务的旧记录不迁入；只转换当前/受保护集合 |
| 旧技术历史查询/重放 | 全历史重建、旧新混读、广泛回放适配 | 不提供被放弃部分的在线详情、逐次同步回放和补发；明确显示T前历史不完整，不补零、不伪造连续历史 |
| 旧证据格式 | 长期多格式读取与全量旧hash重建 | 目标源存储统一新格式；一次性工具只支持保留集合实际出现的格式；必要原ID/hash/原时点及审计证明仍保留 |
| 通用引用登记 | 新建evidence_pins、动态owner/target管理 | 取消该表和通用框架；保留现有FK，固定枚举业务JSON引用，必要时在既有证据行登记保守保留标记 |
| 独立故障生命周期 | 新建incidents及配套状态流程 | 复用job/capture_attempt/现有故障记录，补可信resolved_at、解决依据及关联；无法证明已解决就hold |
| 新增表 | 正文、pins、incidents、daily_rollups四种职责 | 原则上仅正文共享表＋每日汇总/容量表两张；目录复用0055，状态与维护使用现有进程 |
| 旧程序回退 | 广泛混读、反向展开/旧格式转换 | 不开发通用反向转换；无新写时可撤回完整旧库/旧镜像，已有新写后用新格式兼容版本或前向修复 |
| A–F交付 | 六个逻辑批次、可合并部分工程 | 三个交付阶段，统一候选、一次计划内Staging切换，避免按批反复部署 |

**可取消的工作**：全量旧正文规范化、所有旧采集页的重建/去重对账、无价值历史的旧ID兼容目录、任意旧任务重放/补发工具、通用pins平台、独立incident工单流程、全库新旧表示双写、通用v2→v1反向转换。必要的迁移清单/断点、受保护证据转换与验证、旧备份原样恢复能力不能取消。

工作量为方案阶段判断：历史迁移/兼容部分预计减少约50%–70%，整体工程量约减少25%–40%，**不是实测工期或报价**。主要写入逻辑、引用验证、权限/并发/备份恢复和业务验收仍须完成；受保护旧集合若很大或格式复杂，节省会缩小。

## 3. 必须完整保留的集合与最小保护

- 正式订单、报价/商业版本、人工计划、财务/生产/关账、员工操作/权限审计、用户角色权限、附件实际对象及引用：全部保留稳定ID、原业务事实/版本；不把正式审计中已嵌入的事实JSON当可删Raw。
- 当前有效合同/颜色/物料、来源绑定/归属、heads/state/catalog当前指针、最近可信成功/尝试与原调度策略：完整保留。新结构从现有有效事实建立基线，不重新采集覆盖人工数据、不把迁移算作一次同步成功。
- 所有正式业务引用的源证据及传递依赖、订单删除/恢复事件及原完整证明、未解决异常、unknown、在途/待恢复/重试链、必要幂等回执与法律保留：完整保留。必要请求身份不能因历史起点重置而被再次执行。
- **不能只取“最新一条”**：0039到料计划有snapshot复合FK；计划版本/归属证据/任务result有JSON引用；0060生命周期事件依赖前次和确认目录run；capture.directory通过JSON引用chunks。按固定schema递归取闭包，未知引用保守保留或阻止相关范围切换，不能靠置空FK、UUID文本替换或重建订单绕过。
- 目标只对选中源证据转换：保持原ID/原hash及可审核的来源证明；原业务JSON不批量改hash。确需原页重建的受保护证据保留最小manifest/解析器，不为其延伸成通用旧历史平台。无法无损证明的受保护格式必须补支持或阻止该范围切换，不能以“精简”丢弃。

源正文按可信来源/账号/合同/报表语义/规范版本共享，强hash命中还验证等价；采集元数据与业务事实分开。无变化不建业务版本，仍正确更新新鲜度、任务与幂等状态；颜色/审计基线差异写。T后真实变化（含A→B→A）和删除恢复长期保留；不改变双遍、身份、金额/数量/单位与调度频率。

固定引用检查可替代通用pins表，不能替代引用保护：旧JSON在隔离选取时枚举，后续依靠业务写事务登记，TTL不逐批扫描全量业务JSON；正式业务写入须同事务登记必要保留标记/FK，保护祖先正文；未知不清、标记宁可多留，不能自动猜测解除。TTL仍需共享正文零有效引用检查、并发围栏、受控权限/不可变触发器、Dry Run、限速小批次、先汇总再清理。普通辅助维护失败局部退避；必要证明/提交未知仍安全阻断，现有暂停不自动解除。

整改前不再需要在线使用的普通过程详情可只留在90天专项原始备份中，原有保留窗口由该归档覆盖；新库明确按T截断在线历史。仍需在线业务使用或异常恢复的记录必须迁入，不能用离线备份代替必要当前证据。不开发整改前全量统计回填，只保留真实可得的必要统计。

保留期限不变：普通成功7天、无变化详细证据7天、临时诊断/分页检查点7天、已解决失败从**可信解决时刻起30天**、每日汇总90天，全部业务/当前/异常/幂等/法律例外优先。不得用后来一次成功推定所有旧故障已解决。每日表兼容量监控，按attempt幂等计入，未知修正不重复计数；不建设通用统计修订平台。

## 4. 三个实施阶段（全部仍待授权）

1. **统一工程候选（合并A/B/C/D及F监控）**：一组前向migration、同一publisher/reader，完成目录复用、物料正文共享、双hash、轻量确认、差异写、固定引用保护、TTL/汇总/故障分级。自动/手动/重试/恢复全部入口覆盖。以一个主PR为默认，复杂到需要独立验证时再拆；不为减少PR省略关键Gate。
2. **选择性迁移演练（E＋迁移验收）**：完整配对备份先原样隔离恢复验证；在恢复副本生成“必保根＋引用闭包＋不迁入清单”，保留ID、数量/金额/单位、原时点/证据；创建最新合法migration账本的目标库，只装入选中数据并转换选中源正文。流式有限批次＋少量checkpoint即可，不开发通用迁移平台。原库、原备份保持不变。未解决/未知不强行结案，切换前仍须通过现有恢复门禁。
3. **一次Staging切换与组合验收（F）**：先取得明确窗口/停写及Worker操作授权，核对PR172/173等实际整改版本；排空或保全在途，用最终一致快照重跑已验证迁移，再校验业务/附件/全部引用，固定T后切换统一候选。按门禁另行批准恢复Worker；至少两轮自然调度及≥24h容量/备份/恢复观察。功能通过不等于容量通过，不部署Production、不自动合并。

少量保留证据转换及固定引用枚举无法取消，但它们的处理范围从“所有旧记录/任意旧格式”降为“实际必须保留的集合”。核心并发、hash边界、幂等/unknown、受控TTL、业务页面、权限、备份恢复的测试继续按v1.1执行，不以减少测试范围换取工期数字。

## 5. 容量与迁移资源：有利，但尚不能承诺1GB

沿用调查12.336GB、三巨表92.11%，其余表合计约0.974GB。若先保守保留其余表，再加入当前源正文/索引、受保护旧证据H和7/30/90天稳态数据，**初始规划仍按1–2GB评估，<1GB作为理想目标，不是已验证上下界**；H大或7天过程量高仍可能超过2GB。选择性迁移比全历史E1更容易逼近目标，但不能把三巨表全部算成可丢弃，也不能用99.38%审计无变化率推算全部可删比例。95%日增量目标仍需同负载实测。

资源占位例（非测量）：原样恢复副本12.34GB＋紧凑目标2GB＋原备份8GB＋目标备份2GB＋WAL/临时/索引工作区10GB＋安全余量10GB＝**约44.3GB新增，另加对象副本、H超预算及运行增长**。相对v1.1约70.7GB示例可减少约26GB；原live库12.336GB仍占原盘，不重复计入新增预算，原样恢复副本另计。采用独立演练盘/主机，初步按50–60GB＋对象空间核算，执行前以实际备份/保留集合/峰值修正。调查时39.7GB可用不足以据此批准同盘并存；本轮不测新容量、不申请或配置资源。

## 6. 不可逆风险与恢复

不迁入部分在新库不再可查，T前来源变化时间线明确不完整。90天内仅能在隔离原始备份＋匹配旧镜像/代码中恢复旧技术详情，不保证新业务系统继续提供其在线重放；**专项原始配对备份从正式迁移验收成功起保留90天**，到期前再次验证恢复能力、验收及无hold，实际退役另批，日常备份策略不变。

开放新写前，验收失败可取消切换，撤回未变旧库＋精确旧migration账本的旧镜像。开放新写后，不能直接切回冻结旧库：先保护全部新写和附件，使用新格式兼容候选/前向修复；从备份恢复也必须补齐全部已提交业务写，不能以丢失新写换旧程序回退。**不再承诺旧程序一键回退**是本方案明确的能力取舍；无法满足所需恢复窗口时不切换。现有migration checksum/verify-only、唯一owner、权限及恢复门禁全部保留。

## 7. 集中评审范围

建议批准v2作为后续设计路线：以选中集合为新历史起点、两张新表上限目标、三个阶段、取消通用历史/引用/incident/反向转换平台。用户已给定的保留方向不再重复确认；具体迁移集合及放弃清单、目标资源、维护窗口/恢复时限、Staging部署/停写/Worker恢复、旧库/备份退役仍须形成可审操作单后另行授权。本轮仅文档和Issue登记，不代表上述执行获批。
